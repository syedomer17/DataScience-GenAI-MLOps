# PostgreSQL Data Types

This document provides a detailed overview of the core data types supported by **PostgreSQL**, structured for clear understanding and reference.

---

## 1. Numeric Data Types

Numeric types in PostgreSQL are divided into integer (non-decimal) types, arbitrary-precision (decimal) types, and floating-point (approximate) types.

### A. Integer Types (Non-Decimal)

| Data Type | Storage Size | Range | Description |
| :--- | :--- | :--- | :--- |
| **`SMALLINT`** | 2 bytes | -32,768 to +32,767 | Used for small-range integers to conserve disk and memory space. |
| **`INTEGER`** (or `INT`) | 4 bytes | -2,147,483,648 to +2,147,483,647 | The standard choice for integers in most databases. |
| **`BIGINT`** | 8 bytes | -9,223,372,036,854,775,808 to +9,223,372,036,854,775,807 | Used when integer values exceed the range of standard `INTEGER`. |

> [!NOTE]
> **No native `TINYINT` in PostgreSQL:** PostgreSQL does **not** have a native `TINYINT` (1-byte integer, 0 to 255) data type like MySQL or SQL Server. If you need a 1-byte integer, you can use `SMALLINT` (2 bytes) or apply a domain/constraint check (e.g., `CHECK (column_name >= 0 AND column_name <= 255)`) to enforce the same range.

### B. Auto-Incrementing Types (Serial)

Serial types are not true data types, but rather a notation shorthand for creating auto-incrementing columns (backed by PostgreSQL sequences).

| Data Type | Storage Size | Range | Description |
| :--- | :--- | :--- | :--- |
| **`SMALLSERIAL`** | 2 bytes | 1 to 32,767 | Auto-incrementing small integer. |
| **`SERIAL`** | 4 bytes | 1 to 2,147,483,647 | Most common type for auto-incrementing primary keys. |
| **`BIGSERIAL`** | 8 bytes | 1 to 9,223,372,036,854,775,807 | Auto-incrementing large integer. |

> [!TIP]
> Modern PostgreSQL (version 10+) recommends using standard SQL `IDENTITY` columns instead of `SERIAL`.
> **Example:** `id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`

### C. Decimal and Exact Numeric Types

| Data Type | Storage Size | Range / Precision | Description |
| :--- | :--- | :--- | :--- |
| **`NUMERIC(p, s)`** / **`DECIMAL(p, s)`** | Variable | Up to 131,072 digits before decimal; up to 16,383 digits after | Exact numeric representation. Perfect for monetary amounts and calculations requiring absolute precision. |

- **`p` (Precision):** The total number of significant digits (both sides of the decimal point combined).
- **`s` (Scale):** The number of digits in the fractional part (to the right of the decimal point).
- *Example:* `NUMERIC(5, 2)` can store values from `-999.99` to `999.99`.

### D. Floating-Point (Inexact) Types

| Data Type | Storage Size | Precision | Description |
| :--- | :--- | :--- | :--- |
| **`REAL`** | 4 bytes | 6 decimal digits precision | Variable-precision, inexact. It might round off decimal values to fit its precision. |
| **`DOUBLE PRECISION`** | 8 bytes | 15 decimal digits precision | Variable-precision, inexact. Provides a wider range and higher precision. |

## 2. Character and String Data Types

PostgreSQL supports three main string/character types. In PostgreSQL, all three types perform similarly under the hood, meaning there is no performance penalty for using `TEXT` instead of `VARCHAR`.

| Data Type | Description | Space Behavior |
| :--- | :--- | :--- |
| **`CHAR(n)`** / **`CHARACTER(n)`** | Fixed-length, blank-padded. If the stored string is shorter than `n`, spaces are appended to fill the length. | Pads remaining space with blanks. |
| **`VARCHAR(n)`** / **`CHARACTER VARYING(n)`** | Variable-length with a limit of `n` characters. If the string is shorter, it only stores the actual text. | Does not waste or reserve remaining unused space in memory or disk. |
| **`TEXT`** | Variable-length with unlimited length (up to 1 GB). | Recommended for storing any length of text where a limit is not required. |

## 3. Boolean Data Type

| Data Type | Storage Size | State | Accepted Inputs (Case-insensitive) |
| :--- | :--- | :--- | :--- |
| **`BOOLEAN`** | 1 byte | `TRUE`, `FALSE`, and `NULL` (representing unknown/none) | **True:** `TRUE`, `'t'`, `'true'`, `'y'`, `'yes'`, `'1'` <br> **False:** `FALSE`, `'f'`, `'false'`, `'n'`, `'no'`, `'0'` |

## 4. Date and Time Data Types

PostgreSQL has highly sophisticated date and time tracking capabilities.

| Data Type | Storage Size | Description | Example Format |
| :--- | :--- | :--- | :--- |
| **`DATE`** | 4 bytes | Calendar date (year, month, day) without time. | `YYYY-MM-DD` (e.g., `2026-08-29`) |
| **`TIME`** (without time zone) | 8 bytes | Time of day only (no date associated). | `HH:MM:SS` (e.g., `22:22:22`) |
| **`TIMETZ`** (with time zone) | 8 bytes | Time of day with time zone offset. *(Generally not recommended)* | `22:22:22-05` |
| **`TIMESTAMP`** (without time zone) | 8 bytes | Both date and time, without time zone offset. | `YYYY-MM-DD HH:MM:SS` |
| **`TIMESTAMPTZ`** (with time zone) | 8 bytes | Date, time, and timezone. Internally stored as UTC. | `2026-08-29 22:22:22+05:30` |

> [!NOTE]
> **Best Practice:** Always prefer `TIMESTAMPTZ` over `TIMESTAMP` when storing absolute moments in time. PostgreSQL automatically handles conversion based on the client session's local timezone configuration.
